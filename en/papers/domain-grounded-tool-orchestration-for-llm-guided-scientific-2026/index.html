Domain-Grounded Tool Orchestration for LLM-Guided Scientific Analysis

arXiv 2026 53 method

TLDR

An ontology-grounded LLM architecture separates intent, deterministic tool execution, and explanation via MCP for correct CFD and topology analysis workflows.

Reasoning

Strengths include a clear separation of LLM interpretation, deterministic tool execution, and explanation, plus ontology grounding and a second-domain instantiation showing architectural reuse. Weaknesses are that the abstract lacks quantitative results and focuses on CFD post-processing/TDA rather than aerodynamic design or solver modeling.

Deep Analysis

Innovations

  • Separation of intent interpretation (LLM), execution (deterministic domain tools), and explanation (LLM), connected by the Model Context Protocol (MCP).
  • Domain ontologies that constrain planning to valid analysis chains, grounding tool orchestration.
  • Design that by construction removes whole failure classes such as API hallucination and missing pipeline stages.
  • Extensible architecture where adding a second domain required only an ontology and tool wrappers, with no change to architecture, protocol, or deployment.
  • Ablation-based isolation of the ontology's effect: it improves interpretation accuracy rather than tool selection, and only with scoped fact retrieval.
  • ParaView client-server deployment carrying analysis to production-scale datasets through a thin browser client.

Methodology

The paper presents an architecture that decouples LLM-based intent interpretation, deterministic domain-tool execution, and LLM explanation, connected via the Model Context Protocol and grounded by domain ontologies constraining planning. It instantiates this architecture in two domains, CFD post-processing and topological data analysis via TTK, on the same ParaView server infrastructure. An ablation across both domains evaluates tool selection and interpretation accuracy, including scoped versus bulk retrieval of ontology facts.

Key Results

An ablation across both domains shows the ontology does not change which tools the planner selects, but raises interpretation accuracy from 0.41 to 0.91, and only when relevant facts are retrieved in scoped rather than bulk form. Adding the second domain required only an ontology and tool wrappers around existing filters, with no change to architecture, protocol, or deployment.

Limitations

  • Strategic errors remain after the design narrows them.
  • The ontology's corrective effect on interpretation is conditional on scoped retrieval of relevant facts; bulk retrieval does not yield the same benefit.
  • The reported instantiation covers two domains, so broader generalizability is not established in the abstract.
